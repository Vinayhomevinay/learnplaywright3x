CONCEPT 1

Async

The keyword you put in front of a function to tell JavaScript "this one will take time — treat it that way."

Simple definition
async in front of a function means: this function always hands back a Promise, and it's allowed to use await inside itself.
Real-world analogy
◆Marking a function async is like stamping a food order ticket "this one takes time" — the kitchen doesn't hand it to the customer instantly; it knows to come back to it once it's ready.
Technical definition
An async function declaration always returns a Promise. If the function's return value isn't already a promise, it gets implicitly wrapped in one. An async function with no await inside it runs synchronously until it returns.
Code
async-fn.jsnode
async function main() {
  return "hello";
}

main().then(console.log); // "hello" — auto-wrapped in a Promise

Playwright use case
Every single Playwright test callback is an async function: test('login works', async ({ page }) => { ... }). That's this keyword, in literally every test file you'll ever write.
Best practices
Do
  • Mark every Playwright test/fixture callback async by default
  • Let it return a value directly — the Promise wrapping is automatic
Don't
  • Assume async makes code run in parallel — it doesn't, by itself
  • Mix async functions with old-style callback params without a reason
CONCEPT 2

await

The keyword that pauses your function at that exact line, until the Promise next to it settles.

Simple definition
await pauses execution inside an async function until the Promise on its right finishes, then hands you back the resolved value.
Real-world analogy
◆await is standing at the counter until your coffee is actually handed to you — not walking away and assuming it's ready because you ordered it.
Technical definition
An await expression suspends execution of its surrounding async function until the awaited Promise is fulfilled or rejected. The resolved value becomes the result of the expression; a rejection throws, catchable with try/catch. await is only valid inside an async function (or as top-level await in a module).
Code
await.jsnode
function getUser() {
  return new Promise((resolve) => {
    setTimeout(() => resolve({ name: "Vinay" }), 1000);
  });
}

async function main() {
  try {
    console.log("Fetching user...");
    const user = await getUser();
    console.log(user);
  } catch (err) {
    console.log("Error:", err);
  }
}
main();
watch the output below
// click "run this" to see it execute
Playwright use case
Nearly every Playwright API call needs await in front: await page.click(...), await expect(locator).toBeVisible() — because the click or assertion itself returns a Promise that resolves once the browser confirms it happened.
Best practices
Do
  • Await every Playwright action and assertion, no exceptions
  • Wrap awaited calls in try/catch when you need custom error handling
Don't
  • Forget an await — it's the #1 cause of flaky, hard-to-explain test failures
  • Use await outside an async function (outside top-level module await)
CONCEPT 3

Promise.all

Runs several promises at once, and waits until every one of them has finished.

Simple definition
Promise.all runs multiple promises in parallel and waits for all of them to finish. If even one rejects, the whole thing rejects immediately.
Real-world analogy
◆Ordering three dishes at a restaurant table together — the meal is "served" only once the slowest dish is out, and if the kitchen burns one dish, the whole order is flagged as a problem.
Technical definition
Promise.all() takes an iterable of promises and returns one Promise that fulfills when every input promise fulfills, with an array of values in the original order. It rejects as soon as any input promise rejects, with that first rejection reason — the other promises keep running, but their results aren't captured by Promise.all.
Code
promise-all.jsnode
const p1 = new Promise(r => setTimeout(() => r("A"), 1000));
const p2 = new Promise(r => setTimeout(() => r("B"), 2000));
const p3 = new Promise(r => setTimeout(() => r("C"), 1500));

async function main() {
  const results = await Promise.all([p1, p2, p3]);
  console.log(results); // ["A","B","C"] after ~2s (slowest wins)
}
main();

Playwright use case
The classic pattern: await Promise.all([page.waitForNavigation(), page.click('#submit')]) — the click triggers navigation, so you start "watching for navigation" and "clicking" at the same moment, instead of clicking first and risking a missed navigation event.
Best practices
Do
  • Use it only for genuinely independent tasks that can run together
  • Use Promise.allSettled instead when partial failure is acceptable
Don't
  • Expect partial results back if one promise rejects — you lose them all
  • Use it when steps genuinely depend on each other's output
CONCEPT 4

Promise.race

Settles the instant the first promise settles — win or lose — and ignores everyone else.

Simple definition
Promise.race settles as soon as the first promise in the list settles, whether that's a resolve or a reject, and ignores every promise that finishes after it.
Real-world analogy
◆Calling three delivery riders for the same order — whichever one arrives first is the one you deal with; the other two are quietly waved off when they show up later.
Technical definition
Promise.race() takes an iterable of promises and returns a Promise that settles with the eventual state — fulfilled or rejected — of whichever input promise settles first. It marks all input promises as "handled" immediately, so later rejections from the losing promises don't trigger unhandled-rejection warnings; those losing promises keep running in the background, they just aren't cancelled.
Code
promise-race.jsnode
const slow = new Promise(r => setTimeout(() => r("slow done"), 2000));
const fast = new Promise(r => setTimeout(() => r("fast done"), 500));

async function main() {
  const result = await Promise.race([slow, fast]);
  console.log(result); // "fast done" after 500ms
}
main();

// Classic use: race a call against a timeout
const timeout = new Promise((_, reject) =>
  setTimeout(() => reject("Request timed out"), 3000)
);
Promise.race([apiCall(), timeout]);

Playwright use case
Enforcing a custom timeout around a flaky third-party call: race your actual request promise against a timer-based rejection, so a hanging call fails your test fast instead of stalling the whole run.
Best practices
Do
  • Use it specifically for timeout patterns
  • Remember the losing promise's rejection is silently ignored — it won't crash your app
Don't
  • Assume the losing promise gets cancelled — it keeps running
  • Rely on it for "first success wins" — a fast rejection still wins the race (use Promise.any for that)
CONCEPT 5

new Promise

The constructor you use to wrap any operation that isn't already Promise-based.

Simple definition
A Promise is an object representing a value that will exist eventually. It starts pending, then settles as either resolved or rejected — exactly once.
Real-world analogy
◆Ordering food at a counter: you get a token (the Promise) immediately, and later it's either called out as ready (resolved) or the kitchen tells you they're out of stock (rejected).
Technical definition
A promise is said to be settled once it is fulfilled or rejected — never both, and never more than once. If a handler is attached after the promise has already settled, it still fires, so there's no race condition between the async work finishing and a .then()/.catch() being attached later.
Code
promise.jsnode
const myPromise = new Promise((resolve, reject) => {
  setTimeout(() => {
    const success = true;
    if (success) resolve("Data loaded!");
    else reject("Something went wrong");
  }, 1000);
});

myPromise
  .then((result) => console.log(result))
  .catch((error) => console.log(error));

Playwright use case
Wrapping a legacy, callback-based Node API (like an old fs.readFile call, or a third-party SDK that predates promises) in new Promise(...) so it can be awaited inside a Playwright fixture or test step.
Best practices
Do
  • Reach for it only to wrap genuinely callback-based or event-based APIs
  • Always call resolve or reject exactly once
Don't
  • Wrap something that already returns a Promise — known as the "Promise constructor antipattern"
  • Forget to handle the error path with reject
CONCEPT 6

Callback

The original pattern everything else on this page was built to improve on.

Simple definition
A callback is a function you hand to another function, to be called later — usually once some async work (a timer, a file read, an API call) finishes.
Real-world analogy
◆Telling a colleague "text me once the deploy finishes" instead of standing there watching the pipeline yourself.
Technical definition
A callback is simply a function reference passed as an argument to another function, invoked by that outer function at a later point — often after an asynchronous operation completes. There's no built-in error-handling convention; each API decides its own callback signature (commonly (error, result) in Node-style APIs).
Code
callback.jsnode
function getUser(id, callback) {
  setTimeout(() => {
    callback({ id, name: "Vinay" });
  }, 1000);
}

getUser(1, (user) => {
  console.log(user); // runs after 1s
});
watch the output below
// click "run this" to see it execute
Playwright use case
Event listeners: page.on('response', (response) => { ... }) or page.on('console', (msg) => { ... }) — Playwright's event system is still built on plain callbacks, even though its actions use Promises.
Best practices
Do
  • Use callbacks freely for one-off event listeners (page.on(...))
  • Keep the callback body short and focused
Don't
  • Nest callbacks for multi-step async flows — convert to async/await instead
  • Mix callback-style and promise-style handling for the same operation

FAQ

Frequently asked

Is async/await just a replacement for Promises?+
No — async/await is built entirely on top of Promises. Under the hood, an await is still doing the equivalent of a .then(). It's a different way to write the same mechanism, not a different mechanism.
Can I use await outside an async function?+
Only at the top level of a module (top-level await), which most modern setups support. Inside any regular function, await requires that function to be marked async.
What's the difference between Promise.all and Promise.allSettled?+
Promise.all rejects immediately if any promise fails, discarding the other results. Promise.allSettled always waits for everything and gives you a status ("fulfilled" or "rejected") per item — useful when partial failure is acceptable.
Why does my automation script sometimes fail without an error message?+
Usually an unhandled Promise rejection — an await without a surrounding try/catch, or a .then() chain missing a final .catch(). Always wrap awaited calls in error handling in test code.
Which one should I actually use day-to-day?+
async/await for almost everything you write by hand — it's the most readable. Reach for Promise.all when steps are independent and can run together, and Promise.race specifically for timeout patterns. Plain callbacks mostly show up in event listeners you consume, not code you write fresh.
Does Playwright's auto-waiting mean I don't need to understand this?+
No — auto-waiting handles waiting for an element to become actionable (visible, stable, enabled). It doesn't remove the need for await in your own test code; without it, your test's own JavaScript moves to the next line before Playwright's action has even started.
